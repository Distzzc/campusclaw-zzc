## Context

现有 Flask 应用以 `/login` 的 HTML 表单建立 Cookie Session；`before_request` 从 session 读取用户，页面路由和 JSON API 共用该身份上下文。前端 API 请求依靠同源 Cookie，受保护页面模板也接收服务端用户信息。详见 proposal.md 与 `specs/token-based-authentication/spec.md`。

## Goals / Non-Goals

**Goals:**
- 将请求认证统一到显式 Bearer 凭证，并在服务端执行身份解析、期限校验和撤销检查。
- 让现有浏览器页面继续可用，同时不依赖导航请求携带 Authorization 头，也不在无认证页面 HTML 中嵌入用户或材料信息。
- 保持密码哈希校验、角色权限、班级隔离和现有 API 业务行为不变。

**Non-Goals:**
- 不引入 JWT、刷新令牌、跨设备会话管理、多因素认证、SSO 或账号管理能力。
- 不保留 Cookie Session 与 Bearer Token 的双轨兼容期；切换后旧 Cookie 不再授权。

## Decisions

### 使用服务端可撤销的不透明令牌

- 登录 API 校验现有账号密码后，使用 Python 标准库的密码学安全随机源生成不可预测的令牌；响应只返回一次完整令牌。
- 新增令牌记录，至少保存用户 ID、SHA-256 令牌摘要、创建时间、过期时间和撤销状态/时间。服务端不保存完整令牌，数据库泄露时摘要不应直接成为可用凭证。
- 受保护请求对收到的令牌计算摘要并查找有效记录；身份的角色和班级仍从当前用户数据库记录读取，避免客户端声明或过期令牌副本决定授权。撤销状态和到期时间每次请求均检查。
- 初始有效期为 3600 秒。过期或撤销记录可在认证检查之外按安全方式清理；清理不得使已过期令牌重新有效。
- 选择不透明令牌而非 JWT：本应用已有 SQLite，在线查询成本可接受；服务端记录使登出即时撤销并避免将角色/班级权限固定在过期 claims 中。令牌摘要而非原文落库，限制持久化泄漏风险。

### 明确登录、登出与 API 凭证契约

- 新增 JSON 登录端点（建议 `POST /api/auth/login`），接收账号/密码，成功时返回 `access_token`、`token_type: Bearer`、`expires_in` 和现有非敏感用户字段；错误账号和密码沿用相同的错误语义。
- 新增认证登出端点（建议 `POST /api/auth/logout`），依据当前 Bearer 令牌撤销对应记录。受保护 API 只从 `Authorization` 头解析 Bearer 凭证，不从 Cookie、查询参数或表单中回退取值。
- 现有认证装饰器仍负责页面/API 未认证语义、角色授权和当前班级约束，但身份来源由服务端 token lookup 替换为 token 所关联的用户查询。
- 令牌生成、摘要和有效期使用标准库能力；不新增外部依赖。API 响应、异常和访问日志均不得包含完整令牌或密码。

### 浏览器页面使用公开外壳与受保护数据 API

- 登录页保留账号/密码表单，由前端脚本提交 JSON 登录 API；成功后仅将令牌保存在 `sessionStorage`，然后导航到课堂页面。
- `/materials` 导航请求不能携带脚本存储的 Authorization 头，因此改为返回不包含用户身份、班级或材料数据的中性页面外壳。页面脚本读取 token 后调用 Bearer 保护的 `/api/me`；缺少 token 或收到 401 时清除 token 并转至 `/login`。
- 统一前端 API helper 和文件下载请求附加 Authorization 头。登出时先请求撤销 API，再清除 `sessionStorage` 并转到登录页；无论服务端请求失败与否，本地凭证都应清除。
- 选择标签页级 `sessionStorage` 而非 `localStorage`，降低令牌跨浏览器重启的持久时间。它仍可被同源脚本读取，因此需避免注入型脚本风险；HttpOnly Cookie 更能隔离脚本，但与本次全面移除 Cookie 认证的要求不一致。

### 迁移与兼容

- 此变更是有意的破坏性认证切换：部署后所有既有 Cookie 登录态立即失效，客户端必须重新登录；不提供 Cookie fallback 或双轨窗口，以避免行为模糊和意外继续接受旧凭证。
- 现有教师/学生角色限制和班级过滤保持不变，所有原有受保护资源测试改为显式 Bearer 请求；额外验证仅 Cookie、伪造/错误令牌、过期令牌、已撤销令牌均不能授权。
- 数据库初始化以幂等方式创建令牌表，不需要重写既有用户/材料数据；回滚旧版本前应清除前端标签页令牌，旧版本将按原 session 行为要求重新登录。

## Risks / Trade-offs

- [Risk] `sessionStorage` 中的凭证可被同源 XSS 读取 → 继续对模板输出做转义、避免不可信 HTML 注入，并将严格 CSP/更完整的 XSS 防护作为后续安全强化；令牌短时有效且可即时撤销。
- [Risk] 服务端每次 API 请求需查询令牌和用户记录 → 以数据库索引令牌摘要和过期时间满足当前 SQLite 使用规模；若未来性能成为瓶颈，再考虑带撤销策略的缓存。
- [Risk] 认证机制切换会使已登录用户退出，未升级的 API 客户端会收到 401 → 在发布说明中明确重新登录和添加 Bearer 头的要求，按单一切换窗口部署。
- [Risk] 页面外壳变为可匿名获取可能被误认为页面内容受保护不足 → 外壳只含通用 UI，不包含任何用户或材料数据；实际数据仍只由 Bearer 保护的 API 返回。

## Migration Plan

1. 创建令牌记录表和认证服务，先以接口测试确认签发、摘要存储、身份加载、到期和撤销行为。
2. 更新 API 认证中间件和登录/登出端点，将页面身份信息移出服务端模板，并让浏览器脚本负责 token 获取、附加、清除及失效跳转。
3. 更新所有 API、下载和角色/班级隔离测试为 Bearer 认证，同时验证旧 Cookie 不再生效、匿名页面外壳不含敏感数据。
4. 单次部署服务端和前端变更；用户重新登录。回滚时回退到旧认证实现，清理浏览器标签页令牌并要求重新登录；不迁移 Cookie 或 token 状态。
